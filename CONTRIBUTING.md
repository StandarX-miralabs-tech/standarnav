# Contributing to standarnav

standarnav (npm package `@standarx/nav`) is unreleased; v0 is in progress. This
document explains how to set up the project, what is expected of a pull
request, and how to report a bug. Read it before opening a pull request.

## Prerequisites

- [bun](https://bun.sh). The repository pins the version in `.bun-version`
  (`1.4.0`, read 2026-09-18); CI installs that exact version through
  `oven-sh/setup-bun` (`.github/workflows/ci.yml:17-19`). Use that version or
  a newer one. Never use `npm` or `npx` in this repository — every command
  below is a `bun` command.
- A Playwright browser for the browser test project. The default engine is
  Chromium (`vitest.config.ts:9`):

  ```sh
  bun x playwright install chromium
  ```

  Install `firefox` and `webkit` the same way when you need to reproduce the
  CI matrix locally.
- Node is not required to run the scripts below; `bun` runs them directly.

## Setup

```sh
bun install
```

## Scripts

The scripts used for contribution checks, read from the `scripts` field of
`package.json` on 2026-09-18. Run them with `bun run <script>`.

| Script | Command | Purpose |
|---|---|---|
| `dev` | `vite playground --open` | Serve the fixture page in `playground/`. The engine is not wired into it yet: `src/` does not exist. |
| `build` | `tsdown` | Build the package (ESM, unbundled, with `.d.ts`). |
| `typecheck` | `tsc --noEmit` | Type-check without emitting output. |
| `lint` | `biome check .` | Lint and format-check with Biome. |
| `lint:fix` | `biome check --write .` | Lint and fix what Biome can fix automatically. |
| `format` | `biome format --write .` | Format the codebase with Biome. |
| `test` | `vitest run` | Run every test project (unit and browser). |
| `test:unit` | `vitest run --project unit` | Run the Node-based unit tests only. |
| `test:browser` | `vitest run --project browser` | Run the browser tests on one engine, Chromium unless `SNAV_BROWSER` says otherwise (`vitest.config.ts:9`). |
| `test:watch` | `vitest` | Run tests in watch mode. |
| `bench` | `vitest bench --project unit --run` | Run the benchmark suite. |
| `check:size` | `bun run scripts/size-budget.ts` | Measure the min+gzip size of every published entry of `dist/` against its cap. Needs a build first. |
| `check:package` | `bun run scripts/check-package.ts` | Pack the tarball, then run `publint` and `attw --profile esm-only` on it. |

Before opening a pull request, run at minimum:

```sh
bun run lint
bun run typecheck
bun run test
bun run build
bun run check:package
bun run check:size
```

`bun run test` and `bun run build` fail today, because `src/` does not exist
yet: the engine has not been extracted. Until the first extraction commit
lands, CI is red for that reason and not because of your change.

## Conventional commits

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <short summary>
```

Types used in this repository: `feat`, `fix`, `perf`, `docs`, `refactor`,
`test`, `chore`, `ci`.

Scopes describe the area touched, for example `spatial`, `gamepad`, `react`,
`focus-ring`, `keymap`, `modality`, `tabbable`. Use no scope for changes that
span the whole repository (a root `chore` or `ci` change, for instance).

Examples:

```
feat(spatial): add app-mode composite crossing for gamepad
fix(gamepad): correct dead-zone renormalisation at the sector boundary
docs(react): document useIntentScopeHost cleanup order
```

### No AI co-author trailer

Never add an AI co-author trailer to a commit message — no `Co-Authored-By`
trailer generated by a tool, under any name. Authorship trailers are for
human contributors only.

## Release notes

[ADR-0012](docs/adr/0012-versioning-and-release.md) accepts semver starting
at 0.x and proposes changesets as the changelog tool; that tool choice is
still a rider the owner has not closed, and nothing is wired into the
repository — there is no `.changeset/` directory and no release workflow.

Until one is wired, the release note lives in the pull request description:
a pull request that changes anything a consumer can observe carries one
sentence saying what changed for that consumer, in English, and names the
affected subpath rather than the file. That sentence is what the CHANGELOG
entry is written from at release time. A documentation-only or
internal-refactor pull request says so explicitly instead of leaving the
line out.

## Tests are required for every behaviour change

Every change to behaviour needs a test. There is no exception for "obvious"
fixes.

- A change that touches the DOM (focus movement, attribute reads or writes,
  scroll handling, the focus ring overlay) needs a browser test, and it must
  pass on the three engines of the CI matrix: Chromium, Firefox, and WebKit
  (`.github/workflows/ci.yml:61-83`). Locally, `bun run test:browser` runs
  one engine at a time; select the other two with the environment variable
  the configuration reads:

  ```sh
  SNAV_BROWSER=firefox bun run test:browser
  SNAV_BROWSER=webkit bun run test:browser
  ```

  A unit test running in Node is not a substitute for a browser test when
  real DOM APIs (`focus()`, `getBoundingClientRect`, `checkVisibility`,
  `document.activeElement`) are involved. Browser tests are named
  `*.browser.test.ts`; everything else stays in the `unit` project
  (`vitest.config.ts:18-26`).
- Pure functions (geometry scoring, keymap resolution, attribute parsing) are
  covered by unit tests under the `unit` Vitest project.
- A pull request without a test for the behaviour it changes is not merged.

## Size budgets are blocking

The build job of CI runs `bun run check:size` after the build and the drift
gate (`.github/workflows/ci.yml:48-49`). The script is
`scripts/size-budget.ts`. It measures six lines against the built `dist/`:
the core (`index.js`), the gamepad engine, the spatial engine and the focus
ring — each bundled with its sibling entries (`../*`, `../../*`) left
external, so the number is the marginal cost of adding that subpath next to
the core — the debug entry with `./*` external, and one "whole package" line
that bundles the four runtime entries once, through a synthetic re-export
module, with nothing external. Each line is minified and gzipped at Bun's
default level; that reads a little heavier than `gzip -9`, so never mix the
two in one comparison. The script also fails with a clear message when
`dist/` is missing.

Every cap is `null` today. A `null` cap means "measured, not yet capped":
the line is still built and reported, and the run **fails** printing the
measurement, because a cap invented before the first measurement would be a
guess the script then ratifies by staying green
([ADR-0017](docs/adr/0017-size-budgets.md)). So `bun run check:size` is
expected to exit non-zero until the first caps are written from real
numbers, and CI is red for that reason as well.

A pull request that touches a measured entry pastes the `check:size` lines
for that entry into its description, so the size change is visible in review
rather than reconstructed afterwards.

A pull request that would exceed a cap does not raise the cap in the same
change: it either reduces the size, or it links an ADR amendment (see
[ADRs](#adrs-architecture-decision-records)) that proposes and justifies the
new cap. The budget script itself is not the place to negotiate a larger
number.

## No documentation claim without its proof

Every number, benchmark result, or compatibility claim in a Markdown file
needs one of:

- a test that asserts it,
- a measurement with the exact command that produced it and the date it was
  run, or
- a source URL (a spec, a caniuse/MDN entry, a competitor's own repository).

A claim with none of these is written as "not measured yet" or "to be
verified" instead of being asserted. This applies to README, ADRs, the
specification, and the roadmap alike.

## Code and comments

- Code, identifiers, commit messages, and comments are in English.
- No comments by default. Write a comment only when it explains a non-obvious
  WHY that the code cannot express by itself — never a restatement of WHAT
  the code does.

## Markdown: English canonical, French mirror for user documentation

Every committed `.md` file is English. User-facing documentation under
`docs/` follows an additional rule: `docs/en` is canonical, and `docs/fr` is
its strict, file-by-file mirror. A documentation page without its mirror
does not merge — add the French page in the same pull request, or hold the
English page until it is ready.

This mirror rule applies to user-facing documentation only. Governance files
(this one, the code of conduct, the security policy), ADRs, the
specification, and the roadmap stay English-only with no mirror. The policy
and its reasons are recorded in
[`docs/adr/0015-language-policy.md`](docs/adr/0015-language-policy.md).

## ADRs (Architecture Decision Records)

Decisions with lasting consequences (an API shape, a breaking rename, a size
budget, a supported-runtime tier) are recorded as an ADR under `docs/adr/`,
numbered `NNNN-title.md`. An ADR starts with a `# ADR-NNNN: Title` heading,
then `Status`, `Date` and `Deciders` lines, then the sections `## Context`,
`## Decision`, `## Consequences`, `## Alternatives considered` and
`## Evidence` (commands, URLs, dates). The full rules, the numbering, and the
index of the existing records are in
[`docs/adr/README.md`](docs/adr/README.md). Read an existing ADR before
proposing a new one — [`docs/adr/0005-real-dom-focus.md`](docs/adr/0005-real-dom-focus.md)
is a worked example — and link related ADRs by file name from the one you
add.

See also [`docs/specification.md`](docs/specification.md) for the engine
specification and [`ROADMAP.md`](ROADMAP.md) for what is planned versus what
exists today.

## Pull request checklist

Before requesting review, confirm:

- [ ] Commit messages follow Conventional Commits, with an appropriate scope.
- [ ] No commit carries an AI co-author trailer.
- [ ] Every behaviour change has a test; DOM-touching changes pass on
      Chromium, Firefox and WebKit.
- [ ] `bun run lint`, `bun run typecheck`, `bun run test`, and `bun run build`
      pass locally.
- [ ] The `bun run check:size` lines for every entry the change touches are
      pasted in the description, and no cap is exceeded — or the pull request
      links an ADR amendment proposing the new cap.
- [ ] The description carries the one-sentence user-facing change, or states
      that the change is documentation-only or internal.
- [ ] Every number or claim added to documentation carries its proof (test,
      measurement with command and date, or URL) or is marked "not measured
      yet" / "to be verified".
- [ ] New or changed code and comments are in English; no comment restates
      WHAT the code already says.
- [ ] Any new or changed user-facing documentation page under `docs/en` has
      its `docs/fr` mirror in the same pull request.
- [ ] A decision that deserves an ADR has one, linked from the pull request
      description.

## Reporting a bug

Open a bug with the "Bug report" issue template
(`.github/ISSUE_TEMPLATE/bug_report.yml`). It asks for the information a
report needs to be reproduced without a round trip:

1. **A minimal HTML fixture.** A single self-contained `.html` file that
   reproduces the issue with the smallest possible markup and inline styles,
   no CSS framework. The template ships a skeleton to start from.
2. **The runtime.** Browser and version, operating system or TV model, and
   the input device that produced the wrong move (keyboard, d-pad, stick,
   remote, pointer).
3. **Expected versus actual focus**, described concretely: which element
   `document.activeElement` should point to after the move, and which one it
   points to instead.

A report missing the fixture or the runtime information takes longer to
triage and may be sent back for these details before it is investigated.

A device observation with no bug attached (a television or a gamepad you
tested) goes to the "Device report" template
(`.github/ISSUE_TEMPLATE/device_report.yml`) instead: those reports are what
later compatibility claims will point at.
