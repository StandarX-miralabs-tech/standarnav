# 2026-09-18: initialisation of standarnav

## Goal of the session

Decide whether the input system of miralabs-ui can leave that repository and live as an independent
open-source library, and if so, under which name, license, package boundary and browser baseline. No
code was moved today; the session produced verified facts, decisions and the first documents of this
repository. Source under study, read-only: a local clone of miralabs-ui at commit `289fa607`
(334 commits, 2026-09-18).

## What was verified in the source

Every claim of the initial brief was re-read against the source code before being used. Every path,
line number and line count in the table below was read in miralabs-ui at commit `289fa607` on
2026-09-18. Outcome:

| Claim in the brief | Verdict | Evidence |
|---|---|---|
| The engine moves real DOM focus | confirmed | `focusElement()` calls `element.focus({preventScroll:true})` and reads `document.activeElement`, `packages/core/src/input/spatial/spatial.ts` (508 lines) |
| Containers are declared in HTML attributes | confirmed | `packages/core/src/input/spatial/containers.ts` (46 lines): pure parsers `blocksDirection`, `wrapsDirection`, `entryStrategy` (`last \| first \| nearest`, default `last`) |
| Each container remembers its last focused element | confirmed | `WeakMap<HTMLElement, WeakRef<HTMLElement>>`, `spatial.ts:198` and `spatial.ts:235` |
| The orthogonal weights come from Chromium | confirmed for the constants | `DEFAULT_WEIGHT_HORIZONTAL = 30`, `DEFAULT_WEIGHT_VERTICAL = 2` in `geometry.ts`, matching `kOrthogonalWeightForLeftRight` and `kOrthogonalWeightForUpDown` in `third_party/blink/renderer/core/page/spatial_navigation.cc` |
| The scoring formula is Chromium's | nuanced | only the two constants match; the body of `scoreOf` is not Blink's formula |
| Two passes, tvOS style | nuanced | `findBestCandidate` is one loop with two accumulators (`aligned`, `any`) returning `aligned ?? any` — semantically the two-pass rule, not literally two passes. Ties go to DOM order |
| The geometry is independent of CSS | nuanced | true for the scoring only; candidate collection goes through `checkVisibility` and `canScroll` |
| The overlap threshold is lrud-spatial's | confirmed | `DEFAULT_OVERLAP_THRESHOLD = 0.3`, `geometry.ts` (278 lines) |
| The gamepad engine only polls when it must | confirmed | rAF polling in `gamepad/gamepad.ts` (450 lines, `wc -l`, 2026-09-18) runs only while a pad is connected, the document is visible and the plugin is mounted |
| The project is under FSL | wrong | miralabs-ui is MIT since its initial commit (LICENSE, seven `package.json`, README) |
| Five framework adapters exist | wrong | one exists: `packages/react/src/input.tsx` (209 lines). `packages/vue`, `svelte`, `angular` hold only `package.json` + README ("Frozen, post-v1. No src/"); `packages/vanilla` has no input wrapper |
| The extractable unit is the spatial engine | wrong | the unit is the whole input system (intent bus, input system, keymap, engage, gamepad, spatial, focus ring) plus eight modules outside `input/`: `interaction/modality.ts` (180 lines), `focus/tabbable.ts` (113 lines), `dom/event.ts`, `dom/query.ts`, `dom/raf.ts`, `dom/platform.ts`, part of `types.ts`, `utils/invariant.ts` |
| Extraction is a one-way dependency | wrong | dependency inversion: `@miralabs-ui/core` imports `pushEngageScope` (slider, drawer, color-picker, date-field) and `isTextEntryTarget` (drawer, toolbar) **in value**; 17 files in 14 component directories emit `data-mira-nav*` (`grep -rl data-mira-nav packages/core/src/components --include=*.ts`, test files removed) and 9 SCSS files read `html[data-mira-input]` (`grep -rl data-mira-input packages/styles --include=*.scss`), both run 2026-09-18 |
| The written attributes are prefixed | wrong | `data-focused` and `data-nav-active` are unprefixed, `containers.ts:17-18`; the prefix is a frozen constant, not configurable |

Also read and confirmed today at the same commit: the intent bus is a LIFO scope stack where `true`
ends the walk and a `trapped` scope swallows everything except `back`, `tabNext`, `tabPrev` while
`base` scopes are still asked (`intent-bus.ts`, 148 lines); `createInputSystem()` is an instance,
never a singleton
(`input-system.ts`, 219 lines); `keymap.ts` carries webOS Back 461, Tizen Return 10009, Tizen Exit
10182 and channel up/down 427/428, and nothing for Vidaa, Vizio, Roku, Fire TV or Android TV. Missing
tests found in the source: `scrollAndRescan` (`spatial.ts:327-351`), `pointerFollowsFocus`,
`data-mira-nav-scroll="center"`, the whole of `debug.ts` (73 lines, whose winner rule is a
re-implementation rather than a shared one), and right-stick horizontal scroll.

## Measurements

`bun run check:size` in miralabs-ui, 2026-09-18, on a `dist` built the same day, min+gzip with Bun's
default gzip level, externals `../*` and `../../*`:

| Budget line | min+gzip | Cap | Usage |
|---|---|---|---|
| input system (intents + engage) | 1.93 kB | 2.00 kB | 96 % |
| gamepad engine | 2.35 kB | 3.00 kB | 78 % |
| spatial engine | 2.81 kB | 3.00 kB | 94 % |
| modality tracker | 0.74 kB | 1.00 kB | 74 % |

Caveat on those figures: the externals. Reported by a reader agent and not re-measured today, the
spatial engine without externals weighs 3303 B min+gzip, above the 3 kB cap. The scope of each
budget line has to be stated explicitly in this repository before any cap is written down.

Caveat on the bench: `geometry.bench.ts` measures `findBestCandidate` alone — pure arithmetic — on 200
and 2000 candidates (80x40 cells, 90x50 pitch), not `collectNavNodes`, `getBoundingClientRect`,
`querySelectorAll` or `checkVisibility`. The guard in `geometry.test.ts:156-177` (median of 51 samples
under 1 ms) has the same blind spot, so it is not an end-to-end budget. Figures from the 2026-08-27
release notes of miralabs-ui (2.48 kB gamepad, 2.89 kB spatial, 1.34 kB focus ring, 4.3 microseconds
for 200 candidates) are historical, were not re-measured here, and must be labelled as such wherever
quoted.

## Compatibility findings

Version numbers below were fetched from caniuse and MDN browser-compat-data on 2026-09-18; the source
URL of each row is listed in `docs/research/tv-runtime-compatibility.md`.

| API | Chrome | Safari | Firefox | Use in the engine | If absent |
|---|---|---|---|---|---|
| `WeakRef` | 84 | 14.1 | 79 | `spatial.ts:198,235` | used unguarded; the source carries no fallback today |
| `Element.checkVisibility()` | 105 | 17.4 | 106 | `focus/tabbable.ts:41-45` | fallback `offsetParent === null && getClientRects().length === 0` |
| `inert` attribute | 102 | 15.5 | 112 | `focus/tabbable.ts:48-50` | `closest("[inert]")` works everywhere; only the native effect is missing |
| `Array.prototype.at` | 92 | 15.4 | 90 | `focus/tabbable.ts:85` | TypeError |

The build target of the source repository is `es2022` (miralabs-ui `tsconfig.base.json:3`, read
2026-09-18). Combined with the unguarded `WeakRef` and the `Array.prototype.at` call of the table
above, the de facto floor of the source today is Chromium 92. Among the TV runtimes listed below, the
first ones above that floor are Tizen 7.0 and webOS 23, both Chromium 94.

standarnav targets `es2020` instead. Its syntax floor was read on caniuse on 2026-09-18: optional
chaining `?.` lands in Chrome 80, Safari 13.1, Firefox 74 and Samsung Internet 13.0
(https://caniuse.com/mdn-javascript_operators_optional_chaining), nullish coalescing `??` in
Chrome 80, Safari 13.1, Firefox 72 and Samsung Internet 13.0
(https://caniuse.com/mdn-javascript_operators_nullish_coalescing), so the pair sets the floor at
Chrome 80, Safari 13.1, Firefox 74. `Array.prototype.at` lands only in Chrome 92, Safari 15.4,
Firefox 90 and Samsung Internet 16.0
(https://caniuse.com/mdn-javascript_builtins_array_at), which is why the extraction drops it. Every
API above the syntax floor is feature-detected with a fallback.

TV runtimes, from Samsung "Web Engine Specifications"
(https://developer.samsung.com/smarttv/develop/specifications/web-engine-specifications.html) and LG
"Web API and Web Engine" (https://webostv.developer.lge.com/develop/specifications/web-api-and-web-engine),
both fetched 2026-09-18: Tizen 4.0/5.0/5.5/6.0/6.5/7.0/8.0/9.0 = Chromium 56/63/69/76/85/94/108/120;
webOS 4.x/5.x/6.x/22/23/24/25 = Chromium 53/68/79/87/94/108/120. Hisense Vidaa and Vizio SmartCast
publish no Chromium version. The Steam client's embedded Chromium (CEF) was reported at
109.0.5414.120 for the Steam Deck beta client of 2024-01-18
(https://steamdeckhq.com/news/steam-deck-beta-client-1-18-24-descriptions/); no newer version is
disclosed as of 2026-09-18, and the November 2025 rebuild from the Alloy runtime to the Chrome
runtime was confirmed by Valve without a version number
(https://steamcommunity.com/groups/SteamClientBeta/discussions/3/688615792191756981/). Full table
with URLs: `docs/research/tv-runtime-compatibility.md`.

## Name selection

Protocol per candidate, 2026-09-18 between roughly 18:00 and 19:50 UTC:
`Invoke-WebRequest registry.npmjs.org/<name>` (404 = free), the same for `@standarx/<name>` and for
hyphenated variants, `gh api repos/StandarX-miralabs-tech/<name>`,
`gh search repos <name> --match name`, a web search for a product or trademark, and two probes,
`<name>.dev` (DNS) and `<name>.js.org` (HTTP 200 means a catch-all page, so inconclusive). Full
evidence, command by command, in `docs/research/name-availability-2026-09-18.md`.

48 candidates were checked under that protocol on 2026-09-18: 29 free, 8 risky, 11 already taken.

A three-judge panel (product, developer ergonomics, risk), whose scores are published in
`docs/research/name-availability-2026-09-18.md`, scored out of 30 on 2026-09-18: standarnav
23, padnav 22.5, standarpad 21.3. The panel disagreed: developer ergonomics rejected the whole
`standar*` family for the standard/standar typing trap on every import, while risk preferred it for
the absence of the token anywhere on the web.

Adverse fact found and verified with `gh api users/standarx`: a third-party GitHub organisation
`standarx` exists since 2024-12-24 (Brazil, one repository `.github`, 2 followers, site standarx.com
live), predating `StandarX-miralabs-tech`, created 2026-09-18. The risk is on the whole StandarX
family, not on this project alone. No INPI, EUIPO or USPTO trademark search was done.

Owner's decision: **standarnav**, because navigation here is not gamepad-only — it is keyboard,
remote, d-pad, stick and pointer modality — so a pad-centred name would be narrower than the library.
Attribute prefix `data-snav-*`, npm package `@standarx/nav`, repository
`StandarX-miralabs-tech/standarnav`.

## Competitor research

20 fact sheets, each written from the competitor's own source code and then re-verified by a second
agent reading the same code, 2026-09-18. They cover 18 distinct projects: two were surveyed twice
under two npm names, the WICG spatial navigation polyfill and js-spatial-navigation. Committed
summary: `docs/research/competitors.md`. The raw fact sheets and the working comparison table are
not committed; every figure that survives is in the committed summary with the date it was read.

Two headline results:

1. None of the 18 calls `navigator.getGamepads`. Analog stick and gamepad handling is the one axis
   on which none of the surveyed libraries offers an equivalent.
2. Real DOM focus is not a differentiator. Eleven of the 18 focus real DOM elements: BBC
   `@bbc/tv-lrud-spatial`, the WICG `spatial-navigation-polyfill`, its `@sberdevices` fork, the
   CSS Spatial Navigation Level 1 specification as written, `js-spatial-navigation`,
   `@salutejs/spatial`, `@arrow-navigation/core`, Enact Spotlight, Tabster, `@gauntface/dpad-nav`,
   `react-js-spatial-navigation`. Norigin is a twelfth case: virtual by default, real DOM focus
   available as an option.

Weekly-download and star figures used in the sheets were read on the registry and on GitHub on
2026-09-18; Norigin's 38,114 weekly downloads cover 2026-09-10 to 2026-09-16.

## Negative results

- Names already taken, so dropped: rudder, helm, tiller, veer, yaw, binnacle, lodestar, gnomon, wsn,
  gridnav, keynav. `wsn` was the working directory name and is not available as a package name.
- `standarnav.js.org` returns HTTP 200, a catch-all page: the probe proves nothing either way.
- Facts that stayed unverifiable: the Shadow DOM behaviour of Norigin (not tested live), the current
  status of the Chromium flag `--enable-spatial-navigation`, the Chromium versions of Vidaa and Vizio
  TV sets.
- No test has ever run on TV hardware, in the source repository or here.
- The CI of the source repository is down: `gh run list -R miralabs-tech/miralabs-ui --limit 8`
  returns 8 failures out of 8, with the annotation "The job was not started because recent account
  payments have failed or your spending limit needs to be increased." GitHub Actions billing on the
  account that carries the new organisation has to be checked before this repository counts on a
  public CI.

## Tooling and method

The research behind this entry was produced by a multi-agent workflow run on 2026-09-18 that spawned
104 agents; the figure describes the tooling of this session, not the library. The agents were
candidate name generators and probes, competitor readers each paired with an adversarial verifier
reading the same source code, source-code readers, and a three-judge panel for the naming. Agent
output was treated as a lead, not as a fact: every figure, version, path and line number written
above was re-read from its primary source — the miralabs-ui code at `289fa607`, a recorded command
output, or a vendor or caniuse page fetched on 2026-09-18 — before it entered this file.
