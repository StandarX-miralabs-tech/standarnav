# ADR-0004: Relationship with miralabs-ui: consumer, not fork

Status: Accepted
Date: 2026-09-18
Deciders: Wesley Cormier

## Context

[ADR-0003](0003-extraction-scope.md) says what moves out of miralabs-ui. This
ADR says what happens to miralabs-ui afterwards. There are only two honest
answers: it keeps a copy, or it becomes a consumer. Anything in between is two
systems drifting apart.

The engine is not loosely coupled to the design system today. Read on
2026-09-18 in miralabs-ui at commit `289fa607`:

| Coupling | Evidence (all `grep -rl`, 2026-09-18) |
|---|---|
| `pushEngageScope` imported **in value** by four state machines | `components/slider/slider.machine.ts`, `components/drawer/drawer.machine.ts`, `components/color-picker/color-picker.machine.ts`, `components/date-field/date-field.machine.ts` (plus a type reference in `components/dialog/dialog.types.ts` and a re-export in `src/index.ts`) |
| `isTextEntryTarget` imported in value | `components/drawer/drawer.connect.ts`, `components/toolbar/toolbar.connect.ts` (re-exported by `src/index.ts`) |
| Components emitting `data-mira-nav*` | 17 files in 14 component directories: calendar, color-picker, date-field, date-picker, dialog, listbox, menu, pagination, popover, search-field, select, tabs, toast, toolbar |
| SCSS reading `html[data-mira-input]` | 9 files under `packages/styles/scss/`: `components/_accordion.scss`, `_breadcrumb.scss`, `_clipboard.scss`, `_color-picker.scss`, `_date-field.scss`, `_focus-ring.scss`, `_tabs.scss`, `_toast.scss`, `mixins/_focus.scss` |

Two more facts shape the decision. `interaction/modality.ts` (180 lines,
`wc -l`, 2026-09-18) is a ref-counted singleton per document: it holds a
`WeakMap<Document, ModalityState>` and writes the modality attribute on
`<html>`. Two copies loaded in one page would both claim that attribute. And
the intent bus keeps one LIFO scope stack per `createInputSystem` instance; a
component pushing an engage scope into one stack while the application listens
on another is a silent failure, not a type error. Duplication here is not a size
problem. It is a correctness problem.

## Decision

The owner decided on 2026-09-18: **miralabs-ui deletes
`packages/core/src/input/` and depends on `@standarx/nav`.** Engage mode and the
keymap go too. One system, one maintainer, one place to fix a bug.

Migration plan, in order:

1. **Publish `@standarx/nav` 0.x from this repository** with the extracted
   engine and its browser test suite. No miralabs-ui change yet.
2. **Open a branch in miralabs-ui.** Replace every import from `src/input/...`
   with the matching subpath of `@standarx/nav` (`pushEngageScope` from the
   core entry, `isTextEntryTarget` from the core entry, `spatialPlugin` from
   `@standarx/nav/spatial`, `gamepadPlugin` from `@standarx/nav/gamepad`).
3. **Rename the attributes in the same branch.** `data-mira-nav*` →
   `data-snav*` in the 14 component directories listed above; `data-focused` →
   `data-snav-focused`; `data-nav-active` → `data-snav-active`;
   `html[data-mira-input]` → `html[data-snav-input]` in the 9 SCSS files.

   The custom properties are **not** part of this step. `--snav-focus-ring-*`
   names **six** properties inside this repository's plugin: offset, duration and
   easing, the three it reads from the source's own token set (miralabs-ui:
   `packages/core/src/input/focus-ring/focus-ring.ts:84`, `:112`, `:115`), plus
   `color`, `width` and `z-index`, which the overlay substitutes into an inline
   style because the stylesheet that used to paint it stays on the source side —
   see the decision below, taken 2026-09-20. On
   the source side the `--mira-focus-ring-*` family spans 26 SCSS files, of
   which 20 use `--mira-focus-ring-offset` as an ordinary `outline-offset`
   token unrelated to the overlay, and the whole prefix is generated by one
   mixin (`packages/styles/scss/mixins/_props.scss:5`), so three keys cannot be
   renamed selectively without special-casing it. That is a larger decision
   belonging to miralabs-ui's own token layer and it does not ride along with
   this extraction. Note also that `FocusRingOptions` has no `easing` field, so
   after any rename miralabs-ui could not pass its spring through the API and
   would silently fall back to the plugin's `cubic-bezier`.
4. **Replace `interaction/modality.ts` with the published tracker**, before
   deleting anything. This file is the reason the Context calls duplication a
   correctness problem, and it is **not** under `packages/core/src/input/`: it
   sits at `packages/core/src/interaction/modality.ts` and is imported by 64
   files outside the input system. Deleting only `src/input/` would therefore
   leave miralabs-ui running its own ref-counted tracker, writing the modality
   attribute on `<html>`, while `@standarx/nav` ships a second one — exactly the
   forked state this ADR exists to prevent. The root entry of `@standarx/nav`
   re-exports the modality surface those call sites use, so the change is an
   import rewrite and not a new subpath.

   The other modules that travel with the engine are the opposite case and stay
   behind. `focus/tabbable.ts`, `dom/{event,query,raf,platform}.ts`,
   `utils/invariant.ts` and `types.ts` are stateless — pure functions, a
   selector string and type declarations, with no singleton and no attribute to
   claim — and they are general-purpose helpers with 3 to 43 importers each in
   miralabs-ui, most of which have nothing to do with navigation. Two copies of
   `isHTMLElement` in one page is a size question, and a small one; making a
   component library depend on a navigation package for it would be the wrong
   arrow. So miralabs-ui keeps them, this repository carries its own narrowed
   copies, and the boundary stays where the coupling actually is.
5. **Delete `packages/core/src/input/` and its tests**, and drop the removed
   symbols from `packages/core/src/index.ts`.
6. **Run the miralabs-ui browser suite as the safety net.** It is the only
   place where the engine is exercised against real components in chromium,
   firefox and webkit. The branch merges when it is green.

Release policy: **no long alias period.** The rename ships as one coordinated
breaking release of miralabs-ui, announced in its changelog. A compatibility
shim that emits both attribute names is possible but is not planned; it is
added only if the owner asks for it, and then with a stated removal version.

Direction rule, restated so it cannot be read two ways: `@standarx/nav` never
imports anything from miralabs-ui, at any level — no source import, no
dependency, no peer dependency, no dev dependency for tests. miralabs-ui
imports `@standarx/nav`. The arrow never reverses. This is the same boundary
rule as [ADR-0003](0003-extraction-scope.md), seen from the other side.

## Consequences

- One engine exists at runtime. The `modality.ts` singleton, the scope stack
  and the attribute on `<html>` have exactly one owner again.
- A bug found through a miralabs-ui component is fixed here and released here.
  miralabs-ui bumps a dependency instead of patching a copy.
- The release order becomes a constraint: a breaking change in
  `@standarx/nav` must ship before the miralabs-ui release that needs it.
- Applications upgrading miralabs-ui across that release must rename any
  `data-mira-nav*` attribute and any `html[data-mira-input]` selector written
  in their own code. That is the cost of the rename, paid once.
- **Decided 2026-09-20 — focus-ring defaults: the plugin paints itself, and no
  stylesheet ships.** The plugin moved here (miralabs-ui: 254 lines, `wc -l`,
  2026-09-18) while its colours, width, radius and z-index lived in
  `packages/styles/scss/components/_focus-ring.scss`, which stays in
  miralabs-ui, so shipped unchanged the ring would have been invisible for
  anyone who is not a miralabs-ui user. Of the three options — inline default
  tokens, an optional stylesheet, or dropping `focus-ring` from v0 — the first
  was taken. The overlay writes its paint inline and every value falls back to a
  custom property the application can override (`src/focus-ring/focus-ring.ts:51-52`,
  read 2026-09-20):

  | Property | Fallback | Where it comes from |
  |---|---|---|
  | `--snav-focus-ring-color` | `#1a73e8` | Contrast 4.51:1 on white and 4.36:1 on `#0b0b0f`, both above the 3:1 WCAG SC 1.4.11 asks of a non-text indicator |
  | `--snav-focus-ring-width` | `3px` | The ring's own spread. It was 2px, which matched nothing the source shipped |
  | `--snav-focus-ring-z-index` | `1700` | The rung the source stylesheet gave the ring — above its modal, popover, toast and tooltip |
  | `--snav-focus-ring-offset` | `2` | How far outside the target the ring sits, in pixels (`:104-106`) |
  | `--snav-focus-ring-duration` | 260 ms, or 150 ms under reduced motion | `:128-139` |
  | `--snav-focus-ring-easing` | `cubic-bezier(0.22, 1, 0.36, 1)` | `:31`, `:137-138` |

  Show and hide fade over 150 ms through WAAPI, skipped entirely under reduced
  motion (`:147-154`), which replaces the `transition: opacity` that left with
  the stylesheet. Two limits come with the choice and are written at the
  declaration: a custom property of the wrong type makes the whole inline
  declaration invalid at computed-value time with no earlier declaration to fall
  back to, and `forced-colors: active` suppresses `box-shadow`, which an inline
  style cannot work around. The second is a v1 ROADMAP item, not a v0 fix. The
  contract grew from five names to six with the z-index; the table in
  [ADR-0001](0001-name-scope-and-attribute-prefix.md) carries the same six.
- Size budget: the lines that miralabs-ui deletes become lines this repository
  owns, and `scripts/size-budget.ts` here covers them. It does, with seven capped
  lines and no cap left `null`: `bun run build && bun run check:size` run
  2026-09-20 in this repository, min+gzip — core 3.13 of 3.25 kB, gamepad engine
  2.48 of 2.50, spatial engine 3.04 of 3.25, focus ring 1.51 of 1.75, debug 0.40
  of 0.50, react adapter 1.30 of 1.50, whole package 8.77 of 9.00
  ([ADR-0017](0017-size-budgets.md), amendment of 2026-09-20). The older figures
  quoted in this record — input system 1.93 kB of 2.00, gamepad 2.35 of 3.00,
  spatial 2.81 of 3.00, modality tracker 0.74 of 1.00 — come from `bun run
  check:size` in miralabs-ui on 2026-09-18 and are inherited context about
  another repository's build, never a measurement of this package.
- The React adapter (miralabs-ui: `packages/react/src/input.tsx`, 209 lines,
  `wc -l`, 2026-09-18) could not be moved verbatim: it depends on `useDocument()`
  from the miralabs-ui environment context. Its replacement here is written and
  takes the document explicitly — `NavDocumentProvider` accepts a `Document` or a
  `() => Document`, and the seam is the adapter's own
  (`src/react/react.tsx:51`, `:64-110`, read 2026-09-20), so the package depends
  on React and on nothing of the design system, per
  [ADR-0003](0003-extraction-scope.md).

## Alternatives considered

- **Fork and diverge.** miralabs-ui keeps its copy, standarnav evolves on its
  own. Rejected: it is this decision inverted. Two implementations of a scope
  stack and a modality singleton will disagree within one release cycle, and
  every bug will have to be fixed twice, differently.
- **Keep engage mode and the keymap inside miralabs-ui, publish only the
  engines.** Rejected: `engage.ts` pushes a scope onto the intent bus that
  lives in the extracted `input-system.ts`, and `keymap.ts` feeds its keyboard
  source. Splitting them puts the coupling in the seam between two packages
  instead of removing it.
- **Peer dependency instead of a direct dependency.** Considered and kept as a
  possibility, not a decision for today: it would let an application pin one
  engine version across miralabs-ui and its own code, at the cost of an install
  step for every consumer. Revisit when `@standarx/nav` reaches 1.0.
- **A deprecation period with dual attribute emission.** Rejected as the
  default because it doubles the attribute surface in the DOM and in the SCSS
  for months. Available on request, as stated above.
